# Prompt 设计文档

## 1. 设计原则

1. **单一职责**：抽取、归并、回答生成三个 Prompt 互不混合，便于单独迭代与评测。
2. **结构化输出**：全部要求严格 JSON，字段与 `src/schemas.py` 对齐，避免自然语言解析。
3. **可校验**：Prompt 输出必须能被代码校验（如归并结果必须覆盖全部 `member_index`），校验失败自动回退规则实现。
4. **不编造**：回答类 Prompt 明确禁止编造政策数字，不确定内容强制标注 `【待确认：xxx】`。
5. **可离线**：每个 Prompt 都有对应的规则兜底实现，Prompt 不是系统的单点依赖。

模型参数：`temperature=0`、`timeout=60`、`max_retries=1`（`src/llm.py`）。

## 2. 抽取 Prompt（`EXTRACT_SYSTEM`）

```text
你是一名客户成功团队的「群聊问题清洗专家」。你的唯一任务是从群聊记录中抽取【客户侧】真正提出的问题/需求/投诉/故障反馈。

判断规则：
1. 只保留客户（提问方）的诉求，忽略客服/销售/机器人已给出的回答、寒暄、表情、系统消息。
2. 同一客户在同一轮里反复追问同一件事，只输出一次。
3. 保留原始业务名词（如产品代号、套餐名、订单号），但去掉问候语和语气词。
4. 把每条诉求改写成一句完整、可独立阅读的中文问句或需求句（不超过 40 字）。
5. 若一段话包含多个互不相关的诉求，拆成多条。
6. qtype 只能取：咨询 / 需求 / 故障 / 投诉。

严格输出 JSON，不要任何解释性文字：
{"questions": [{"text": "...", "qtype": "咨询", "speaker": "客户昵称", "turn_index": 0}]}
```

User Prompt 模板（`build_extract_user`）：

```text
【群聊记录】共 N 条，格式为「序号 | 发言人 | 时间 | 内容」：
0 | 发言人:王女士 | 时间:2026-11-10 09:02 | 请问一下这个退款要怎么操作？
1 | 发言人:客服小李 | 时间:2026-11-10 09:02 | 您好，退款需要提供订单号哦
...

【业务背景】我们是 SaaS 财务软件公司，客户是中小企业财务负责人
```

### Few-shot（写入 System Prompt 的隐性约束，另在文档中保留完整示例）

| 输入 | 期望输出 |
| --- | --- |
| `客服小李：您好，退款需要提供订单号哦` | 不输出（我方回答） |
| `王女士：退款大概多久能到账` | `{"text": "退款大概多久能到账", "qtype": "咨询"}` |
| `李工：登录不上去了，一直提示验证码错误` | `{"text": "登录失败并提示验证码错误", "qtype": "故障"}` |
| `陈经理：强烈建议增加子账号权限管理` | `{"text": "希望增加子账号权限管理", "qtype": "需求"}` |
| `客户：都三天了还没到，太差了` | `{"text": "退款/发货三天未到，客户不满", "qtype": "投诉"}` |

`turn_index` 的作用：把抽取结果回指原始消息，用于展示「客户原声」与来源，也为后续「上下文继承」提供依据。

## 3. 归并 Prompt（`MERGE_SYSTEM`）

```text
你是「重复问题归并专家」。输入是已经初步聚合的问题簇（每簇含若干条不同问法），
你需要判断并输出最终的问题清单。

要求：
1. 语义相同或诉求一致的问题必须合并；仅是措辞、错别字、语气不同，一律视为同一问题。
2. 为每个问题给出规范问法 canonical：动宾清晰、20 字以内、去掉口语（例如「退款要走什么流程」）。
3. category 只能取：售后退款 / 价格费用 / 物流配送 / 功能使用 / 账号权限 / 技术故障 / 发票合同 / 其他。
4. tags 给出 1~3 个检索关键词。
5. 不要新增输入中不存在的问题，不要漏掉任何 member_index。

严格输出 JSON：
{"clusters": [{"canonical": "...", "category": "售后退款", "tags": ["退款", "流程"],
               "member_index": [0, 3, 7], "reason": "三者问的都是退款流程"}]}
```

User Prompt：

```text
【候选问题簇】
[0] 候选规范问法：退款申请入口与退款到账时效？ | 出现 5 次 | 原话：退款怎么操作；退款流程是什么；...
[1] 候选规范问法：发票如何开具、开票周期是多久？ | 出现 3 次 | 原话：发票怎么开；开票大概要几天；...
```

**关键设计**：Prompt 要求输出 `member_index` 而不是直接输出文本，代码可以据此：
- 精确还原每个簇包含哪些原始问题（可追溯、可解释）；
- 校验是否覆盖全部候选，漏项则拒绝该结果并回退规则归并（防止 LLM 丢数据）。

## 4. 回答生成 Prompt（`ANSWER_SYSTEM`）

```text
你是资深客户成功经理，正在编写客户问题的话术草稿，供人工修改后回复客户。

要求：
1. 中文回答，2~4 句，先给结论/可执行步骤，再补充注意事项。
2. 不得编造具体政策数字；不确定的信息用【待确认：xxx】标注。
3. 涉及退款、赔偿、合同条款时，必须提示以官方审核结果为准。
4. 语气专业、简洁、可复制到群里直接回复，不要出现「作为 AI」等字样。
5. 若提供了历史同类问题的人工回答，优先复用其中的口径与术语。
```

User Prompt 模板：

```text
【问题】退款 / 售后政策与操作流程是什么？
【客户原始问法】
- 退款怎么操作
- 退款流程是什么
- 退款大概多久能到账
【历史人工回答】
1. 可在订单详情页申请退款，1~7 个工作日到账
【业务背景】SaaS 财务软件，客户为中小企业财务
请输出回答正文。
```

## 5. ReAct 模板（Agent 推理轨迹）

本项目把 ReAct 的「Thought → Action → Observation」固化为图节点的 Trace 结构，
每一步都写入 `state["trace"]`，并在 UI / CLI 中展示：

```text
Thought:  已有消息但还没有问题清单，下一步应抽取客户问题
Action:   extract_questions
Action Input: {"turn_count": 44}
Observation: 抽取到 30 条客户诉求（模式：deepseek:deepseek-chat）

Thought:  已有关键问题，下一步需要做语义归并，把重复问法合并
Action:   cluster_questions
Action Input: {"threshold": 0.55}
Observation: 合并为 8 个问题簇，最大簇 7 条同义问法
```

与标准 ReAct 的差异：
- **Action 由图结构约束**，只能在已注册的 8 个工具中选择（防止模型幻觉出不存在的工具）；
- **循环终止由代码判定**（`decide_next`），而不是依赖模型输出 `Final Answer`，稳定性更高；
- 同时保留 ReAct 的可解释性：每一步的思考理由都被显式记录，可用于答辩复盘与失败定位。

## 6. 迭代记录

| 版本 | 问题 | 调整 | 效果 |
| --- | --- | --- | --- |
| v1 | 只给「抽取客户问题」一句话 Prompt，模型把客服回答也当问题 | 增加角色判断规则 + Few-shot + `qtype` 枚举约束 | 客服话术误抽显著减少；配合代码侧昵称识别，E05 用例通过 |
| v1 | 归并让模型直接输出合并后的数组，无法追溯到原始消息 | 改为输出 `member_index`，由代码重组 | 归并可追溯，且能做覆盖完整性校验 |
| v2 | 模型偶尔返回带 ```json 包裹或前后废话的内容 | 增加「严格输出 JSON」约束 + `extract_json` 容错解析 | 解析成功率提升；非法 JSON 自动降级规则模式 |
| v2 | 归并漏项（模型只合并了一部分候选） | 增加覆盖校验：`set(covered) != 候选数` 即回退 | 杜绝「合并后问题消失」这一类严重问题 |
| v3 | 回答生成编造退款时效、开票天数 | 增加「不得编造数字 + 【待确认】标注」规则 | 输出可用于对外沟通的草稿，风险可控 |
| v3 | 无网络/无 Key 时整条链路不可用 | 每个 Prompt 配规则兜底（问句线索、主题词典、话术模板） | 离线模式 12/12 用例通过，可现场演示 |

## 7. 离线兜底策略

| Prompt 能力 | 离线替代实现 |
| --- | --- |
| 问题抽取 | 问句线索词 + 故障词 + 需求词 + 客服昵称过滤 + 多人重复消息去重 |
| 归并命名 | 9 类主题词典（每个主题预置规范问法），未命中走相似度聚类 |
| 建议回答 | 主题 × （问题 / 咨询）话术模板，历史回答命中时附加「历史口径参考」 |
