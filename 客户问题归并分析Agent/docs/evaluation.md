# 评测记录与失败分析

## 1. 评测方法

- **评测对象**：离线规则模式（无 API Key，结果确定可复现）。在线 LLM 模式只需配置 `DEEPSEEK_API_KEY`，
  用同一套用例脚本即可复跑（`LLMClient` 自动切换，评测逻辑不变）。
- **评测脚本**：`eval/run_eval.py`，用例定义在 `eval/cases.py`，结果自动写入 `docs/eval_results.md`。
- **判定标准**（每条用例需同时满足）：
  1. **归并正确性**：`expect_groups` 中每个关键词组必须出现在同一个问题簇（规范问法 + 全部原始问法）中；
  2. **规模约束**：问题簇数 ≤ `max_clusters`，抽取问题数 ≥ `min_questions`（防止漏抽/过抽）。
- **指标定义**：
  - 合并率 = 1 − 问题簇数 / 抽取问题数（衡量重复问题的压缩效果）；
  - 归并召回 = 期望同组关键词被合并进同一簇的比例；
  - 误合并率 = 人工抽查中「语义不同却被合并」的簇占比。

## 3. 失败案例复盘

以下均为开发过程中真实出现并被修复的问题，按「现象 → 根因 → 修复 → 验证」记录。

### F1｜首版归并完全失效：29 条问题 → 29 个簇

- **现象**：首次跑样例数据，29 条诉求生成 29 个问题簇，一条都没合并。
- **定位**：用 `embed_texts` 实测同义问法的余弦相似度：
  `退款怎么操作` vs `退款多久到账` = 0.091；`退款流程是什么` vs `退款申请提交在哪里` = 0.078；
  `发票怎么开` vs `开票周期能不能缩短` = 0.000。字符 n-gram 向量在短中文问句上几乎不重合。
- **根因**：模型侧假设错误——以为「相似度聚类」可以独立完成语义归并，但无 embedding 模型时字面重合度太低。
- **修复**：引入主题意图词典（9 类主题，含规范问法），同主题 + 同诉求性质直接合并；相似度仅作长尾兜底；
  并增加「上下文继承」：无主题词的追问沿用同一发言人 3 轮内的主题。
- **验证**：样例数据合并率 0% → 73%；E01/E09 用例通过。

### F2｜故障陈述被整条丢弃

- **现象**：`验证码根本收不到`、`登录不上去了，一直提示验证码错误` 等消息没有进入问题清单。
- **根因**：`_is_question` 只按问号与疑问词判断，客户陈述故障时往往不带问号。
- **修复**：增加 `PROBLEM_HINTS`（报错 / 失败 / 收不到 / 转圈 / 空白 …），抽取数 22 → 30。
- **验证**：E02 通过；样例中登录类问题从 1 条变为 7 条，成为 P0 Top1。

### F3｜评测首轮 2 条未通过（E03 / E12）

- **现象**：E03 只抽到 2 条诉求（`开票大概要几天` 未命中）；E12 缺少「导出」簇（`导出是空白的` 未命中）。
- **根因**：词典缺少「几天 / 几日 / 空白」等口语线索。
- **修复**：补齐 `QUESTION_HINTS`、`PROBLEM_HINTS`；不动算法逻辑。
- **验证**：12/12 通过。

### F4｜建议回答与问题类型错配

- **现象**：「退款 / 售后政策与操作流程」是咨询类问题，却生成了故障排查话术。
- **根因**：话术模板用簇的 `qtype`（取组内最高严重度）选择，而命名用的是「问题 / 咨询」性质，两者口径不一致。
- **修复**：在归并阶段显式写入 `kind`（issue / ask），命名与话术统一使用 `kind`。
- **验证**：样例 8 条建议回答全部与问题语义匹配。

### F5｜客服话术被当成客户问题

- **现象**：`您的是什么格式？`、`需要先筛选数据再导出` 进入问题清单。
- **根因**：只按文本判断，缺少说话人角色信息。
- **修复**：从昵称推断角色（含「客服 / 助手 / 官方 / 销售 / 顾问」视为我方），并叠加「回答式话术」过滤。
- **验证**：E05 通过；样例误抽从 8 条降为 0 条。

### F6｜通用对象类问题（按钮 / 页面 / 商品信息）完全不合并

- **现象**：输入 6 条「按钮坏了怎么办 / 按钮不能用 / 页面不对 / 按钮有bug / 商品信息不对 / 页面出问题」，
  面板只显示 2 条诉求、合并率 0%，另外 4 条完全没有出现。
- **根因**：① 问题识别只认问号与固定故障词，「页面不对 / 有bug / 出问题」未命中，直接被丢弃；
  ② 归并只按业务主题词典，词典外的对象（按钮 / 页面 / 商品信息）没有归类依据，只能各自成簇。
- **修复**：扩充故障词表（不对 / 有bug / 出问题 / 坏了 / 有问题 …）；新增「问题对象」归并：
  剥离「坏了 / 不能用 / 不对 / 有bug / 出问题 / 怎么办」等描述词，抽出对象作为分组键，
  同类合并为「XX相关问题」，单条也保留成行，做到「只归类、不隐藏」。
- **验证**：同一输入 → 客户诉求 6 条，输出 3 类（按钮 3 条 / 页面 2 条 / 商品信息 1 条），可逐类展开查看原话。

## 4. 已知局限

| 局限 | 影响 | 后续方向 |
| --- | --- | --- |
| 主题词典为规则维护，覆盖不到新业务主题 | 新主题问题不会合并，只走相似度兜底 | 用 LLM 动态生成主题，或从历史数据聚类出主题词表 |
| 本地哈希向量语义能力有限 | 长尾同义句可能不被合并 | 接入 BGE / text-embedding-3 后效果显著提升（接口已留好） |
| 完全相同的一句话只计一次（按人 + 文本去重） | 刷屏式重复不会放大频次 | 可增加「同一人 1 分钟内连续相同」的计数策略 |
| 未做超长文档分片 | 单次数万条消息会超出模型上下文 | 按 80 条/块切分后分批抽取再统一归并 |
| 在线 LLM 模式未在本次环境实测 | 无 Key，仅验证了降级路径 | 配置 Key 后执行同套用例并对比合并率 |

## 5. Langfuse Trace 使用

1. 在 `.env` 配置 `LANGFUSE_PUBLIC_KEY` / `LANGFUSE_SECRET_KEY` / `LANGFUSE_HOST`；
2. 每个图节点由 `@observe(name=...)` 包裹，自动上报一条 span（含输入 State 摘要与输出摘要）；
3. 在 Langfuse 面板按 `session_id` 过滤，即可看到 `perceive → plan → extract → ... → finalize` 的完整链路与耗时；
4. 未配置 key 时，Trace 写入 `data/traces/{session_id}.jsonl`，字段为
   `step / time / thought / action / action_input / observation`，可直接作为答辩举证材料。
